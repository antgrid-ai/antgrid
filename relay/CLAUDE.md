# Relay (`relay/src/`)

Deep reference for the relay. Root `CLAUDE.md` holds the repo-wide gotchas,
commands, and conventions — this file loads only when working under `relay/`.

What may be written in any `CLAUDE.md`, this one included, is governed by
*Maintaining these files* in the root `CLAUDE.md`.

v3 protocol: single-frame `hello` auth, epochs, account-derived routing, streams. The v2 register/challenge stack is gone.

- `server.ts` — WS listener: the first text frame MUST be a signed `hello` (anything else → `PROTOCOL_VIOLATION` + close 1008; 10s hello-or-die timer). The verification sequence is written as numbered steps in the source and MUST NOT be reordered — the reasoning for each position, notably why the replay record lands only after the signature verifies, is on the step it belongs to. `relayHost` binds the normalized upgrade `Host` header, which is why a reverse proxy has to preserve it (Caddy's default) or every hello signature fails. Config enforces `replayTtlMs ≥ 2·clockSkewMs` at load. Also serves `POST /internal/{revoke,expire}` for web push. Pinned by `tests/hello-auth.test.ts` and `tests/hello-smoke.test.ts`.
- **Error contract is law:** every relay error frame carries required `retryable`; only auth/protocol failures close the socket — stream and routing errors leave it open.
- `connections.ts` — live connections only (an entry exists iff the socket is open and past hello; no tombstones). Epoch arbitration per deviceId, plus the freshness guard that must run before it, is documented at the code and pinned case-by-case by `tests/epochs.test.ts` — including that equal-epoch admission is load-bearing rather than a tie-break, and that the `helloTs`/`helloNonce` pair is not redundant with the replay cache. Two identity rules span services and so live here: an AGENT's deviceId is its account `deviceUuid`, while an APP's is a per-machine slot `<accountDeviceUuid>#<machineDeviceUuid>` — `verifyAppToken` deliberately does not bind it, which is what lets one app hold a socket per machine without superseding itself. **Never assume `hello.deviceId` is an account device id**: anything driven by one (revocation) goes through `getByAccountDevice`, which collects the bare holder AND every slot scoped under it. **No cascade close** — on agent disconnect its same-account app peers get `peer-offline` and their sockets stay open.
- `replay-cache.ts` — `(deviceId, nonce)` TTL cache (`replayTtlMs`, capacity-bounded) backing hello replay rejection.
- `license/` — the gate is enforced at agent `hello`; apps present their account token too (required). Mechanism is at the declarations and pinned by `tests/license/`: JWKS caching and its kid-miss throttle (`jwks-cache.ts`), the Ed25519 verify with alg and issuer pinned (`verify.ts`), the gate's deviceUuid/pubkey comparison and its cache (`gate.ts`, `cache.ts`). Four facts cross a service boundary and so live here. `licenseIssuerUrl` is web's PUBLIC origin and a DISTINCT config key from `licenseApiUrl`, which the relay uses only to fetch JWKS and may be an internal address; `verify.ts` mirrors web's `jwt-bearer.ts` and the two must stay in lockstep. Better-Auth `client_credentials` tokens carry **no `sub`/`jti`** — device identity is the custom `deviceUuid` claim and the per-credential id is `azp`. The relay reads no entitlement claim at all: `sessionLimit` is gone, so relay license checks are purely identity and validity. And `/internal/revoke` takes the bare ACCOUNT device id **plus the revoking `userId`**, because the device row is unique on `[userId, deviceId]` — one phone image signed into two accounts yields two rows whose app slots differ, so dropping the account scope evicts the wrong one while a `getByDeviceId` lookup would leave a revoked phone routing. Same scope on `LicenseCache.markRevoked`. A verdict failure closes 1008 and is `retryable:false`; `LICENSE_UNAVAILABLE` is infrastructure, not a verdict, and is retryable.
- `authz.ts` — `mayRoute(sender, target)` is the ONLY routing authorization: both sides proved account identity at hello, so routing reduces to same-account. A denied target and an offline target get the identical `PEER_OFFLINE` — an unauthorized sender must never be able to distinguish denial from absence (no presence oracle). `tests/authz.test.ts` pins it, including that a missing uid on either side denies.
- Streams — `stream-open` (agents only) is **unmetered but not unbounded**, and the two are different invariants; both are documented at the code and pinned by `tests/streams.test.ts`. What spans repositories is the naming rule: `SESSION_LIMIT_EXCEEDED` is retired but RESERVED in antgrid-wire's `ErrorCode`. The relay never emits it, but bridge and app still decode it from relays predating the worker cap, so **the name must never be reused for a new meaning**. The paid axis is a worker cap enforced by web at device registration, never here — see web's security-invariants paragraph. Admission stays await-free (single-threaded TOCTOU discipline); any future check must keep that. The relay never parses streamIds out of routed frames — the `{s, m}` envelope is sealed.
- `rate-limiter.ts` — per-IP connection limits + token-bucket on routed binary frames AND JSON text messages (`MESSAGE_RATE_LIMITED`, retryable; **the frame is DROPPED and only the sender is told**, so the peer waiting on a reply learns nothing — see below). Routed frames are keyed per **(pair, channel)**, not per pair: `pairKey` sorts, so one bucket per pair is shared by both directions and every channel, and a preview page load (dozens of subresources) then starves the control plane. Push delivery keeps its own budget (`MessageRateLimiter`, `RATE_LIMIT_PUSH_PER_SEC`) precisely so widening the preview budget never widens a third-party fan-out control.
- **A dropped routed frame is unrecoverable at the relay and only partly recoverable above it.** `RouteHeader` carries no message id and the error frame's `ref` is already claimed by stream-id dispatch, so neither end can learn *which* frame died. Recovery is therefore end-to-end and approximate: the app re-sends idempotent preview requests under the ORIGINAL `requestId` after a short grace, and the bridge's `TunnelManager` outbox replays the response it already produced rather than re-running the upstream fetch. Adding a message id to the route header is the only thing that would make this precise — until then, never assume a `MESSAGE_RATE_LIMITED` can be correlated to a request.
- Client-IP resolution — the resolver is antgrid-wire's `client-ip.ts`, shared with web and pinned there; `TRUSTED_PROXY_IPS` is parsed once at load by the same `parseTrustedProxies` web uses, so the two services cannot drift on syntax or shape (`tests/config.test.ts`). Behind a reverse proxy every peer is the proxy's address, collapsing the per-IP connection limit into one shared bucket, so the set has to be configured — but **keep it as narrow as possible: every HOST inside a trusted range can forge its own reported client IP**, so a whole subnet is acceptable only when all its containers are first-party. Unset = header ignored, and a directly exposed relay must never honour it.

**Security invariant:** no agent admission without a verified license JWT bound to the hello pubkey (sig + license gate; the cache never marks an entry valid until both verify and pubkey-bind complete); apps authenticate with their own account token. The gate answers *is this device who it says it is and still entitled to connect* — nothing past hello re-checks entitlement, so no verb may be made to depend on a quota the relay does not hold. Routing is account-derived only (`mayRoute`, checked fresh on every routed frame) — no vouching step, no per-peer grant to revoke — and an agent disconnect immediately severs routing (`peer-offline`) without closing the app's socket.
