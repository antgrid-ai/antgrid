# Web (`web/src/`)

Deep reference for the licensing/account service. Root `CLAUDE.md` holds the
repo-wide gotchas, commands, and conventions — this file loads only when
working under `web/`.

What may be written in any `CLAUDE.md`, this one included, is governed by
*Maintaining these files* in the root `CLAUDE.md`.

- `env.ts` — Zod env loader (`JWT_SIGNING_SEED` ≥43 chars, `RELAY_INTERNAL_SECRET` ≥16). `TRUSTED_PROXY_IPS` (comma IPs/CIDRs) is parsed to `Cidr[]` at load by antgrid-wire's `parseTrustedProxies` — the same loader the relay uses, so the two cannot drift — and feeds `util/client-ip.ts`, the spoof-safe X-Forwarded-For resolver shared with the relay (peer must be a trusted proxy; walk right-to-left; empty set = header ignored; a fallback taken with a header present warns, throttled per kind). It keys `/events` rate buckets, sign-in-email requester IPs, and geo/country detection; never take a leftmost XFF hop directly. `app.ts` also rewrites `X-Forwarded-For` to the resolved single hop before handing a request to Better-Auth — `/api/auth/*` is publicly reachable, so the cross-device plugin must not be the only thing standing between a forged chain and a stored requester IP.
- `db/` — `PrismaClient` factory (Prisma 6, `engineType="client"` + `runtime="bun"`, `@prisma/adapter-pg`, generated at `src/generated/prisma/`). Schema in `prisma/schema.prisma`; migrations via `prisma migrate` (`bun run migrate`). `Tx = PrismaClient | Prisma.TransactionClient` (alias `SqlRunner`) so helpers take client or tx. Fields camelCase; columns snake_case via `@map`. Tests use ephemeral DBs (`tests/helpers/pg.ts`: raw `postgres` only for CREATE/DROP, then `prisma migrate deploy`).
- `crypto/` — `hmac.ts` only. **There is no custom JWT signer here.** Device tokens are minted by Better-Auth's OAuth provider, configured in `auth/oauth-provider.ts` (`jwks.keyPairConfig` pins `EdDSA`/`Ed25519`, `m2mAccessTokenExpiresIn` is the TTL); the only Ed25519 code we own is the *verify* side, `auth/jwt-bearer.ts` (`jose`, `alg` pinned to `EdDSA`). Anything looking for a signing helper is looking for the plugin's config.
- `auth/` — Better-Auth, session cookie `better-auth.session_token`, CORS. `middleware.ts` gates routes via `auth.api.getSession({ headers })`.
- `auth/cross-device-plugin.ts` — custom cross-device magic-link sign-in (bundled `magicLink` can't span browsers). Endpoints under `/api/auth/sign-in/cross-device/`: `start` (Browser A → row in `pending_sign_in`, httpOnly bind cookie, email link), `approve` (Browser B confirms via `internalAdapter`, errors as `APIError("BAD_REQUEST")`), `status` (Browser A polls → mints session + `setSessionCookie`, marks consumed). Nonce + browser-token stored as HMACs; `timingSafeEqual` compare. Cookie: `<row.id>.<browserToken>`.
- `auth/better-auth.ts` email+password — secondary to the magic link and OAuth, and the only path that can create a user whose address we have **not** already proven; hence `autoSignIn: false` + `requireEmailVerification: true`. The squatter attack this defends, and why the emailed verification link is exempt, is on `purgeUnprovenPasswordCredential` (`models/credential.ts`); `tests/routes/password-auth.test.ts` pins the flows. Two things are easy to undo from elsewhere and so live here: it must be called at BOTH flips of `emailVerified` a squatter could ride — trusted-social linking (`databaseHooks.account.create.before`) and magic-link approve (`cross-device-plugin.ts`) — and **every `/ui/*` password form needs its own `tokenBucket` AND the router's same-origin check**, because `auth.api.*` bypasses the Better-Auth router, so neither `rateLimit.customRules` nor its CSRF middleware ever runs for them. `advanced.backgroundTasks.handler` keeps the send off the response path: otherwise a known address answers a ZeptoMail round trip slower than an unknown one, and a mail outage fails OAuth user creation from inside its try.
- `routes/` — `devices` (`POST/GET /account/devices`, `DELETE /account/devices/:id`, `GET /account/me`), `agents` (`/account/agents`, `/account/devices/me/{peers,heartbeat}`), `projects` (`POST /account/projects/bindings`, Bearer-gated — the bridge reporting where a repository sits on one machine; `GET /account/projects` beside it takes either carrier, since reading which projects exist is not a claim only the holding machine can make), `tasks` (`/tasks*`, `/labels*` — behind `requireUserOrBearer`, so the app's cookie
and the bridge's device token reach the same router; `POST /tasks/:number/runs` is
Bearer-only, enforced by requiring the `deviceId` only that arm sets),
`keys` (`/account/keys`, `/account/keys/rotate`), `subscriptions`, `oauth-handoff`, `oauth-start`, `ui` (server-rendered HTMX), `health`. There is **no** RFC 8628 device-flow / `/activate/*` route — devices are added simply by a signed-in user calling `POST /account/devices` (session gate + both caps — the paid `worker_limit` on `kind:"agent"` rows, and the `app_device_limit` abuse bound on `kind:"app"` rows; see below); the only sign-in approval is the cross-device magic-link `approve`. JWKS is served by Better-Auth's `jwt` plugin at `/api/auth/jwks` (not a custom route).
- `models/` — one file per aggregate; `ls src/models/` is the list. `pending-sign-in` has a 10-min TTL, replay-protected via `consumed_at`. Note the `WebhookEvent` model (table `webhook_events`) has **no accessor module here** — billing writes it through Prisma directly and the inbound-webhook accessors live in `integrations/webhook-events.ts`, so do not go looking for `models/webhook-event.ts`. `checkCapAndUpsert()` holds a per-user advisory lock (`pg_advisory_xact_lock(hashtext(userId))`) inside `prisma.$transaction` then `device.upsert` — closes the count→insert TOCTOU window. Both caps are counted by one query under that lock; never add a cap check outside it.
- `integrations/` — the GitHub App's inbound half. The route verifies and records; nothing is applied on the request path. Two properties are load-bearing and invisible from the call sites: the dedup key is a **hash of the raw signed bytes** (`X-GitHub-Delivery` is a header, so a captured `(body, signature)` pair replays for ever under fresh ids), and `recordDelivery`'s `ON CONFLICT` re-arms an unprocessed row so a manual redelivery is the recovery path rather than a duplicate. This is deliberately the opposite shape from billing, which stamps `processedAt` at insert inside the effect's own transaction. `github-inbound.ts` drains it: rows claimed one at a time under `pg_advisory_xact_lock(hashtext('ghhook:' || id))` — transaction-scoped, so N instances are safe without electing a leader — bounded by `MAX_WEBHOOK_ATTEMPTS` and filtered to `GITHUB_HANDLED_EVENTS`. The types in `GITHUB_DEFERRED_EVENTS` are recorded unprocessed on purpose and are never claimed. `github-drain-loop.ts` is the scheduled runner over both: it repeats the drain until a pass claims nothing, bounded by a pass count AND a wall clock so one invocation can never run unbounded, then purges processed rows past the retention cutoff. It is invoked from OUTSIDE the process (`bun run drain:github-webhooks`) — never an in-process timer, which would put the backlog on the event loop that has to answer GitHub inside its delivery timeout and would swallow the failure exit code that is this service's only alert. `github-import.ts` is the payload → `src/tasks/merge.ts` mapping, deliberately pure so the provider-space half needs no Postgres; the drain's `issues`/`issue_comment` arms do the read-merge-write under `pg_advisory_xact_lock(hashtext('tasksync:' || taskId))`, which `merge.ts` requires of every caller and which the delivery's own `ghhook:` claim does not provide, plus `taskimport:<accountId>:<externalId>` around the does-it-exist-yet read so two drainers holding two deliveries for one new issue cannot both create. Locks are always taken in that order — `ghpoll:`, `ghhook:`, `taskimport:`, `task:`, `tasksync:` — and `hashtext` is one global int4 namespace, so a new prefix has to be picked against every existing one. Import is one-way — `MergeResult.push`/`labelsPush` are dropped, phase 5 owns the outbox — and every refusal on the way in (unknown installation, unknown repo, `syncEnabled` off, a pull request, out of import-filter scope, a task the user unlinked) is a DROP that marks the row processed, never a throw that burns the attempt ceiling. Assignees resolve through `models/integration-identity.ts` once per delivery, before the import filter and before the snapshot mapping: a member outranks provider order for the single column pair, `assigned_to_member` means at least one assignee resolved to a member, and `remoteSnapshot.assignees` carries the full remote array for display only — never merged, since GitHub allows ten assignees and we keep one. **Setting `source: "github"` and the external columns on an imported task is a security property, not provenance decoration**: the app's launch sheet reads them to decide a body is untrusted and must be seen by a human before it becomes an agent's opening instruction.
- `models/integration-identity.ts` — the ONLY thing entitled to turn a provider login into a `user` row. Better-Auth's `account` stores the provider's numeric user id and never the login, so `resolveProviderIdentities` matches on that id and requires the user to hold an **active membership of the integration's own account** — that filter is the security property of the file, and without it one tenant's issue lands on another tenant's member. The table's unique is `[integrationId, externalUserId]`, deliberately not the globally-unique `[provider, externalUserId]` the plan wrote: two accounts can each have issues assigned to the same GitHub user, and one shared row carrying a `userId` is that same cross-tenant mis-assignment arriving through identity instead of routing. Resolution is one-way (`COALESCE` in the upsert, never an unlink) and identities are upserted in sorted order, because `ON CONFLICT DO UPDATE` holds a row lock to commit and payload order would deadlock two drainers whose issues name the same people in different orders.
- `tasks/sync-op.ts` — the outbox's data verbs. Every local writer of a task enqueues through `enqueueForTask`, which resolves the target once per edit through `resolvePushTarget` — four refusals (unlinked, `pushEnabled` off, a repository belonging to another account, a revoked installation), none redundant. `setTaskLabelsInTx` is the one deliberate silent writer: its only caller is the inbound importer, and enqueueing there pushes the provider's own state back at it. Enqueue is **diffed against the row** and `status` is diffed in provider space, so `in_progress → blocked` queues nothing. `kind` is a closed Zod-discriminated set (no `issue.assignees`, no `comment.create` — both are trust-copy changes, not schema changes), and `ARRAY_VALUED_OP_KINDS` is data rather than a name match, because "never replay an array-valued PATCH from the payload as stored" is enforced far from here. Everything that changes WHICH op is next runs under the same `tasksync:<taskId>` key `merge.ts` requires — no fourth lock prefix — and enqueue/cancel require the caller to hold it already, in the transaction writing the task. Three rules are load-bearing: **supersede rather than queue** (a pending, unattempted op of the same kind is rewritten in place, keeping its `seq` and taking a fresh `opKey`, which is also the version token the drain's second critical section compares); an op with `attemptedAt` set is never rewritten, since its outcome is unknown; and the claim reads each task's **lowest pending `seq`** rather than the globally-oldest `nextAttemptAt`, or an op that fails once backs off past its successor and the value the user replaced wins permanently. The claim leases by pushing `nextAttemptAt` forward, because the advisory lock dies at commit and the provider call happens after it. **Throttling never touches `attempts`** — `throttleOp` and `failOp` are separate verbs for that one reason.
- `integrations/github-issues.ts` + `github-push-policy.ts` — the outbox's write seam and its rate policy, driven by `tasks/apply-op.ts`. The writer is an interface so the drain is testable without a network, signs with an **installation** token only, and its `GithubIssuePatch` has **no `assignees` field by construction** — a pushed assignee array is a non-convergent loop with no detector, since GitHub drops an assignee lacking push access and answers 200. `listAppIssuesSince` resolves a create whose response was lost from the primary store with `state=all`, never `GET /search/issues` (eventually consistent in exactly the fast retry window, its own 30/min budget, and `q=antgrid:op:<key>` is not valid free text). It fails closed on the page ceiling, because the caller's next move on an unresolved create is to post. The policy's two rules: **throttling is an outcome distinct from failure** and must never touch `attempts` (which is why `util/rate-limit.ts` is the wrong thing to reuse — it answers a boolean, not a time), and a **rate 403 is told from a permission 403 by which headers are present**, since GitHub gives both the same status. The write budget is a rolling window rather than a token bucket: a bucket sized to 500/hour admits a thousand writes in its first hour. `writes/hour` binds first, then `writes/minute`, then the primary limit; the points budget never binds a write.
- `tasks/publish.ts` — the publish path: which repositories may receive an issue, and the one transaction that binds a task to one and queues `issue.create`. Targets join on **`IntegrationRepo.projectId`** and are addressed from `IntegrationRepo.repoKey`, which the install flow writes from the provider's own granted-repo list — never `Project.repoKey`, which a device asserts about a folder on a developer's machine. `pushEnabled` is required at the offer point as well as at send time, or the toggle offers a choice `applyOp` will silently cancel. **`publish` is a required boolean on `POST /tasks` with no server-side default** and `publishNewByDefault` is never read there: a default that can decide the outcome is the auto-publish the whole design rules out. `already_linked` counts `syncState === 'pending'` even with a null `externalId` — that is a create already in the outbox, and the identity arrives only when the drain writes the response back. Publishing also refuses a device credential (`PUBLISH_REQUIRES_SESSION`): only the Bearer gate sets `deviceId`, and the required field records an intent rather than proving who formed it.
- `tasks/apply-op.ts` + `integrations/github-echo.ts` + `tasks/push-blocked.ts` — the outbox's executor and the two guards it needs. The shape is fixed: **lock → read → decide → commit → HTTP → lock → re-read → verify → write**. Two critical sections, never one, because a transaction held across a third party's latency pins a connection and an advisory lock and stalls the webhook drain behind it. **The pre-push re-fetch is the compare-and-swap** GitHub does not offer (`If-Match` does not exist on issues); when `remote != base` the push is abandoned and the fetched issue goes through `mergeFetchedIssue` so a conflict raised by a push abort is recorded by the same code, with the same lock and the same stickiness, as one raised by a webhook. The second critical section compares **two** version tokens: a moved `remoteSnapshot` writes nothing, a moved `opKey` still writes the observation — our push landed, and dropping it leaves the base behind our own write so its echo merges as a stranger's. **Echo suppression keys on WHAT was written, never when**: `githubIssueEchoHash` over the push RESPONSE (GitHub normalizes what it stores, so hashing the request never fires), and the `updated_at` scheme it replaces silently drops a human's edit our blind PATCH clobbered a second earlier. The re-fetch and the hash are complements — without the first we destroy the edit, without the second we raise a conflict against ourselves — so ship both or neither. `push-blocked.ts` counts pushes that returned 200 and changed nothing (GitHub drops an assignee lacking push access, and ignores `state_reason` unless the state changes) and stops sending the field at `PUSH_BLOCK_THRESHOLD`; it lives on the **task**, not the op, because ops are superseded and a counter on one resets every time the user retypes the value. Its blind spot is deliberate: a push whose target is already correct in provider space returns exactly what was asked and reads as clean — only provider-space merging in `merge.ts` catches that one. The block has **no expiry** — a timer would restart the loop the count exists to stop — so `POST /tasks/:number/push-block/clear` is its only exit, and it lifts the marker and re-queues the value together: the op that carried the field was cancelled when the block was read, so lifting alone leaves the value saved here and nowhere else for ever.
- `tasks/sync-drain-loop.ts` — the outbox's scheduled runner (`bun run drain:task-sync`), invoked from OUTSIDE the process for the same two reasons the webhook drain is. It claims, hands each op to `applyOp`, and stops; nothing about what a push means is reopened here. **An empty claim pass is not an empty queue** — `claimNextOps` applies its `limit` BEFORE the try-lock filter, so a pass whose candidate tasks are all held by another instance claims zero rows while a backlog exists. Copying the inbound drain's zero-row stop therefore lets a second instance silently truncate the first's work; the stop condition is `IDLE_PASSES_BEFORE_STOP` consecutive empty passes separated by a pause long enough for a contending claim transaction to commit, and the reason it is named `idle` rather than `queue_empty` is that the weaker claim is the only one the query supports. **`MAX_CONSECUTIVE_THROTTLES` is the only ceiling on a misread 403**: `throttleOp` never increments `attempts` by design, so a permission 403 classified as a rate limit retries for ever with nothing retiring it. (`MIN_THROTTLE_WAIT_MS` in the policy is the separate half of that: it stops a `Retry-After: 0` or a stale `x-ratelimit-reset` from making the loop a hot one. One bounds the rate, the other the duration.) It is counted per op per invocation, pushed out durably through `throttleOp` and never `failOp` (a wait is not an attempt), and is consequently the only alarm that path can ever raise. **One `createWriteBudget()` and one installation token per integration, per invocation** — the budget is process-local and non-durable, so one per pass enforces nothing; the writer resolves lazily and its rejection is memoized per integration, which is what keeps a revoked installation's ops on `applyOp`'s clean cancellation instead of burning five attempts against credentials that no longer exist. A local budget refusal ends the invocation rather than counting against the op. `taskSyncDrainNeedsAttention` is the exit-code contract: `gaveUp`, `refused`, `throttleCapped` — never an ordinary failure, which stays claimable, and never a bound cutting the run short.
- `integrations/github-install.ts` — the outbound half: binding an installation to an account. `installation_id` arrives as a query parameter on the callback and is not evidence of anything; the App JWT would answer for *every* installation of the App and the session answers for the wrong identity, so ownership is established by exchanging the callback's `code` for a user-to-server token and accepting the id only if `GET /user/installations` lists it. That requires the App to be registered with **"Request user authorization (OAuth) during installation"** — without it no `code` arrives and the flow has nothing to check. Deliberately not one transaction: `upsertIntegrationRepo` reports a repo-key conflict from a unique violation, and Postgres aborts the surrounding transaction on that regardless of the JS catch, losing the repositories that were fine. Discovery is not consent — every repository is recorded `syncEnabled: false` and the consent columns are create-only, so re-running the flow never overwrites an answer. `markMissingReposRemoved` refuses an empty `present` set, so a provider read that silently returns nothing cannot disable every import on the account. The App private key is a cross-tenant master key: env only (`githubAppConfig`), never logged, never leaves `github-app.ts`, and its JWTs are backdated 60s with GitHub's maximum ten-minute `exp`. Note `GITHUB_APP_CLIENT_*` are the App's OAuth credentials and are NOT the `GITHUB_CLIENT_*` sign-in pair.
- `integrations/github-poll.ts` + `github-poll-loop.ts` — the reconcile poll (`bun run poll:github`), the only thing that reads an issue no delivery carried. A webhook describes the future only, so a repository switched on today has a backlog GitHub will never send, and a delivery lost to an outage or to `MAX_WEBHOOK_ATTEMPTS` is gone unless something re-reads the source; **the first import and the repair are one walk from different starting points**, which is why `lastCursor: null` and a stored cursor take the same path. Three properties are load-bearing. `direction=asc` on the listing makes a partial walk a **prefix**, so a run stopped by a page ceiling, a wall clock or a rate refusal still leaves a cursor the next run resumes from — descending order could not advance a cursor until the whole walk finished, so a repository past the ceiling would re-read its first pages for ever. The resume subtracts `POLL_OVERLAP_SECONDS` from the stored cursor, because `since` has one-second resolution against GitHub's clock: re-listing an unmoved issue writes nothing (`remote == base`) while missing one is silent and permanent, and for the same reason the cursor **never moves backwards** and stops advancing at the first item whose `updated_at` will not parse. `lastFullSyncAt` is written ONLY on a short page — every other ending is a prefix. Import goes through `github-inbound.ts`'s own `importIssue`, exported for this and never copied: the `[accountId, externalProvider, externalId]` lookup, the `taskimport:` lock, the import filter and the assignee resolution are the whole idempotency mechanism, and a second implementation is two answers to "have we seen this issue". The `ghpoll:` claim is a **try** lock in a transaction of its own, released before the first HTTP call — it collapses two runners that arrive at once and nothing more, and the durable guard is `taskimport:` behind it. Reads spend `GITHUB_READ_POINTS` against the points budget, never the write budget the outbox needs. `etag` is deliberately untouched: a conditional request got wrong stops importing silently.
- `relay/` — internal push client to revoke/expire device tokens. `util/rate-limit.ts` — bounded in-memory token bucket (10k keys, evict on refill).
- `util/repo-key.ts` — validator half of `bridge/src/repo-key.ts`; the bridge normalizes a remote, web only shape-gates what arrives. Deliberately duplicated rather than shared, because `packages/antgrid-wire` is Apache-2.0 and that boundary is one-way (`LICENSING.md`). The two can only drift silently, so `tests/util/repo-key.test.ts` states real bridge outputs and refusals.

**Tests need Postgres** (`PG_DATABASE_URL`) + the generated Prisma 6 client (`src/generated/prisma/`, regen `bun run --filter antgrid-web prisma:generate` after schema changes — `bun run migrate` only applies migrations). `pretest` regenerates client + Vite assets; tests clone one migrated template DB (`tests/helpers/preload.ts`).

**Asserting that a query is rejected:** use `rejection()` (`tests/helpers/rejection.ts`), never `expect(...).rejects`, which does not survive Prisma's promises — it wedges the runner and every hook after it, so one assertion reads as the whole file hanging. The helper's doc comment has the evidence.

**Security invariants:** device JWTs Ed25519-signed, TTL from `m2mAccessTokenExpiresIn` (`auth/oauth-provider.ts`); tokens are short-lived OAuth `client_credentials` access tokens (re-minted via `/api/auth/oauth2/token`, no `/tokens/refresh` route); revocation is via `DELETE /account/devices/:id` plus the relay `/internal/{revoke,expire}` push, and `requireBearerJwt` re-resolves the token's `deviceUuid` to a live device owned by the verified `uid` on every request — without that read a revoked device keeps its access for the rest of the token's hour, so the lookup is not an optimization to cache away. It sets `deviceId` on the context; a route still proves any device id in its own BODY separately, since the gate's value names the caller, not the target; device-cap checks run inside a tx with per-user advisory lock (anti-TOCTOU). One cap per device kind, **both enforced here at `POST /account/devices`, never at the relay**: `worker_limit` (the PAID axis — machines an account may run an agent on, counted as active `kind:"agent"` rows) vs `app_device_limit` (an abuse bound over active `kind:"app"` rows, never shown in pricing — each app row mints an OAuth client and lands in `listAppDevicePeers`, which every bridge receives in full). A registration is only ever measured against its own kind, so a full phone ceiling can never refuse a build machine. Over-cap → 402 `WORKER_CAP` / `APP_DEVICE_CAP`; keep the two codes distinct, since only `WORKER_CAP` can be resolved by upgrading. No cap claim travels in the device JWT. Registration-time enforcement is deliberate: a cap checked at connect or `stream-open` strands a machine mid-work. `tests/routes/devices-create.test.ts` pins the per-kind behaviour, including that neither ceiling can refuse a registration of the other kind.
