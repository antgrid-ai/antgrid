# Web (`web/src/`)

Deep reference for the licensing/account service. Root `CLAUDE.md` holds the
repo-wide gotchas, commands, and conventions — this file loads only when
working under `web/`.

- `env.ts` — Zod env loader (`JWT_SIGNING_SEED` ≥43 chars, `RELAY_INTERNAL_SECRET` ≥16). `TRUSTED_PROXY_IPS` (comma IPs/CIDRs) is parsed to `Cidr[]` at load by antgrid-wire's `parseTrustedProxies` — the same loader the relay uses, so the two cannot drift — and feeds `util/client-ip.ts`, the spoof-safe X-Forwarded-For resolver shared with the relay (peer must be a trusted proxy; walk right-to-left; empty set = header ignored; a fallback taken with a header present warns, throttled per kind). It keys `/events` rate buckets, sign-in-email requester IPs, and geo/country detection; never take a leftmost XFF hop directly. `app.ts` also rewrites `X-Forwarded-For` to the resolved single hop before handing a request to Better-Auth — `/api/auth/*` is publicly reachable, so the cross-device plugin must not be the only thing standing between a forged chain and a stored requester IP.
- `db/` — `PrismaClient` factory (Prisma 6, `engineType="client"` + `runtime="bun"`, `@prisma/adapter-pg`, generated at `src/generated/prisma/`). Schema in `prisma/schema.prisma`; migrations via `prisma migrate` (`bun run migrate`). `Tx = PrismaClient | Prisma.TransactionClient` (alias `SqlRunner`) so helpers take client or tx. Fields camelCase; columns snake_case via `@map`. Tests use ephemeral DBs (`tests/helpers/pg.ts`: raw `postgres` only for CREATE/DROP, then `prisma migrate deploy`).
- `crypto/jwt.ts` — Ed25519 signing via `jose`; `importJWK` memoized per `SigningKey` (WeakMap). Exports `DEVICE_TOKEN_TTL_SECONDS`.
- `auth/` — Better-Auth, session cookie `better-auth.session_token`, CORS. `middleware.ts` gates routes via `auth.api.getSession({ headers })`.
- `auth/cross-device-plugin.ts` — custom cross-device magic-link sign-in (bundled `magicLink` can't span browsers). Endpoints under `/api/auth/sign-in/cross-device/`: `start` (Browser A → row in `pending_sign_in`, httpOnly bind cookie, email link), `approve` (Browser B confirms via `internalAdapter`, errors as `APIError("BAD_REQUEST")`), `status` (Browser A polls → mints session + `setSessionCookie`, marks consumed). Nonce + browser-token stored as HMACs; `timingSafeEqual` compare. Cookie: `<row.id>.<browserToken>`.
- `auth/better-auth.ts` email+password — secondary to the magic link and OAuth, and the only path that can create a user whose address we have **not** already proven; hence `autoSignIn: false` + `requireEmailVerification: true` (a session before verification hands out the ProductAccount `user.create.after` just provisioned). **A password set on an unverified user is unproven and must not survive someone else proving that address** — `purgeUnprovenPasswordCredential` (`models/credential.ts`) drops it at both flips of `emailVerified` a squatter could ride: trusted-social linking (`databaseHooks.account.create.before`) and magic-link approve (`cross-device-plugin.ts`). The emailed verification link is exempt on purpose — it is delivered to the address in question, so opening it *is* the proof sign-up lacked. `advanced.backgroundTasks.handler` keeps the send off the response path (otherwise a known address answers a ZeptoMail round trip slower than an unknown one, and a mail outage fails OAuth user creation from inside its try). Every `/ui/*` password form carries its own `tokenBucket` **and** the router's same-origin check: `auth.api.*` bypasses the Better-Auth router, so neither `rateLimit.customRules` nor its CSRF middleware ever runs for them.
- `routes/` — `devices` (`POST/GET /account/devices`, `DELETE /account/devices/:id`, `GET /account/me`), `agents` (`/account/agents`, `/account/devices/me/{peers,heartbeat}`), `keys` (`/account/keys`, `/account/keys/rotate`), `subscriptions`, `oauth-handoff`, `oauth-start`, `ui` (server-rendered HTMX), `health`. There is **no** RFC 8628 device-flow / `/activate/*` route — devices are added simply by a signed-in user calling `POST /account/devices` (session gate + both caps — the paid `worker_limit` on `kind:"agent"` rows, and the `app_device_limit` abuse bound on `kind:"app"` rows; see below); the only sign-in approval is the cross-device magic-link `approve`. JWKS is served by Better-Auth's `jwt` plugin at `/api/auth/jwks` (not a custom route).
- `models/` — `device`, `device-oauth`, `agent-inventory`, `product-account`, `plan`, `subscription`, `billing-customer`, `webhook-event`, `pending-sign-in` (10-min TTL, replay-protected via `consumed_at`). `checkCapAndUpsert()` holds a per-user advisory lock (`pg_advisory_xact_lock(hashtext(userId))`) inside `prisma.$transaction` then `device.upsert` — closes the count→insert TOCTOU window. Both caps are counted by one query under that lock; never add a cap check outside it.
- `relay/` — internal push client to revoke/expire device tokens. `util/rate-limit.ts` — bounded in-memory token bucket (10k keys, evict on refill).

**Asserting that a query is rejected:** use `rejection()` (`tests/helpers/rejection.ts`), never `expect(...).rejects`, which does not survive Prisma's promises — it wedges the runner and every hook after it, so one assertion reads as the whole file hanging. The helper's doc comment has the evidence.

**Security invariants:** device JWTs Ed25519-signed, TTL = `DEVICE_TOKEN_TTL_SECONDS`; tokens are short-lived OAuth `client_credentials` access tokens (re-minted via `/api/auth/oauth2/token`, no `/tokens/refresh` route); revocation is via `DELETE /account/devices/:id` plus the relay `/internal/{revoke,expire}` push; device-cap checks run inside a tx with per-user advisory lock (anti-TOCTOU). One cap per device kind, **both enforced here at `POST /account/devices`, never at the relay**: `worker_limit` (the PAID axis — machines an account may run an agent on, counted as active `kind:"agent"` rows) vs `app_device_limit` (an abuse bound over active `kind:"app"` rows, never shown in pricing — each app row mints an OAuth client and lands in `listAppDevicePeers`, which every bridge receives in full). A registration is only ever measured against its own kind, so a full phone ceiling can never refuse a build machine. Over-cap → 402 `WORKER_CAP` / `APP_DEVICE_CAP`; keep the two codes distinct, since only `WORKER_CAP` can be resolved by upgrading. No cap claim travels in the device JWT. Registration-time enforcement is deliberate: a cap checked at connect or `stream-open` strands a machine mid-work.
